# 구조와 상태

## 구성

- `config.js`: 환경 변수 검증. 토큰·키 원문을 로그에 출력하지 않습니다.
- `store.js`: SQLite 스키마 1, 트랜잭션, 실행 잠금, 비밀 본문을 담지 않는 작업 큐와 감사 기록.
- `database.js`/`store-base.js`: 프로젝트 DB 선택과 공통 저장소 계약. 기본값 SQLite, 선택 MySQL이며 동시 기록/실패 시 대체를 하지 않습니다.
- `mysql-store.js`/`mysql-worker.js`/`mysql-schema.js`: MySQL2 전용 워커·연결, InnoDB 트랜잭션·스키마·문법 변환. 생성 열의 고유 키로 활성 당첨 자리 제약을 유지하며 연결 잠금으로 같은 DB의 복수 실행을 막습니다.
- `vault.js`: AES-256-GCM. `prize:이벤트:자리`, `proof:당첨:버전`을 AAD로 사용해 암호문 교체를 차단합니다.
- `draw.js`: 세 번의 Fisher–Yates 섞기, 균등 보안 난수 선택, 비복원 추출.
- `engine.js`: 권한·자격·시간·추첨·검수·지급 상태 전이. Discord 클라이언트 없이 테스트할 수 있습니다.
- `discord-transport.js`: REST 역할 확인, 공개·관리·DM 메시지, 첨부 재업로드, 전송 결과 대조.
- `interactions.js`: init 설치·setting 관리 명령, 비공개 버튼·선택 메뉴·입력창, 검수 버전 확인과 권한 재검사. ui:home은 개인 응답을 삭제하며 공개 안내를 복제하지 않습니다.
- `panel.js`: 초기설정 완료 시 선택한 채널의 안내 게시·갱신·이전 안내 정리. 서버 입장·재시작 시 자동 게시하지 않습니다.
- `setup.js`: init의 채널·역할 팝업, 실행자별 초안과 비공개 최종 확인. 완료 버튼에서 채널 권한·관리 권한·동시 설정 변경을 재확인한 뒤 저장·게시합니다.
- `ui.js`: 안내에서 이어지는 개인 이벤트·당첨·관리 화면과 Label/File Upload 입력창.
- `drafts.js`: 템플릿 선택, 단계별 신청과 자동 상품 순서, 최종 확인, 관리자 템플릿 편집.
- `replies.js`: 멘션한 당첨 안내 답장의 reroll/리롤 명령. DB 작업의 메시지/채널/서버와 실제 봇 작성자를 대조하고 최신 관리 역할을 재확인합니다. 지급 완료·전송 불명은 기존 엔진 규칙으로 차단합니다.
- `main.js`: Gateway Guilds/GuildMessages intent, DB 실행 잠금, 5초 주기 타이머와 재시작 복구. Message Content 특권은 요청하지 않습니다.

## 이벤트

`DRAFT → PENDING → STARTING → RUNNING → DRAWN → COMPLETED`

`PENDING → REJECTED`, 진행 중에는 취소 조건을 만족할 때 `CANCELLED`가 됩니다. 신청자는 원문을 모두 등록해야 PENDING으로 이동할 수 있습니다. STARTING은 게시 작업과 DB의 중간 상태입니다. 게시 성공 후 RUNNING으로 전환합니다. 전송 중 응답이 유실되면 같은 nonce·알림 번호로 메시지를 대조합니다.

## 당첨 자리

일반: `ANNOUNCING → CLAIMABLE → READY → PREPARING → SENDING → DELIVERED`

인증: `CLAIMABLE → SUBMITTING → REVIEW → READY → PREPARING → SENDING → DELIVERED`

- `SUBMITTING`: 버튼 클릭 또는 보완 요청부터 300,000ms.
- 기한 내 명령으로 접수한 첨부는 `UPLOADING`으로 예약하고 최대 60초 동안 내려받습니다. 이 기간에 제출 마감이 지나도 이미 접수한 자료를 리롤하지 않습니다. 실패하면 원래 기한으로 복귀하며 재시작 중인 업로드도 같은 규칙으로 복구합니다.
- `REVIEW`: 검수 대기. 기한 없음. 보완 시 기존 자료를 삭제하고 SUBMITTING으로 이동합니다.
- `CLAIMABLE` 시간 초과 또는 `SUBMITTING` 시간 초과는 EXPIRED, 최종 거절은 DENIED입니다.
- EXPIRED·DENIED 자리의 상품은 그대로 AVAILABLE이 되어 다른 사람을 추첨합니다.
- 당첨 이력의 고유 키는 `(event_id,user_id)`입니다. 다른 이벤트의 당첨 이력은 후보 판정에 사용하지 않습니다.
- 전달 확정 실패는 DELIVERY_FAILED, 네트워크 결과 불명은 DELIVERY_UNKNOWN입니다.
- PREPARING 재시작은 미전송이므로 재시도 가능 상태, SENDING 재시작은 결과 불명 상태로 복구합니다.
- DELIVERED와 원문 삭제는 같은 트랜잭션에서 반영합니다.

상품 slot은 고정이며 당첨 시도 claim은 매번 새로 생성합니다. 수령하지 않은 이전 당첨자의 버튼은 상태 확인으로 차단합니다. 지급 완료한 자리는 리롤하지 않습니다.

## 권한 경계

모든 사용자 동작은 서버 ID와 이벤트의 서버 ID를 대조합니다. 관리자 역할은 매 요청 최신 REST 멤버 조회로 확인하고 검수 승인 시도마다 재확인합니다. 인증 조회는 관리자만, 상품 등록과 미지급 회수는 주최자만 할 수 있습니다. 관리자 목록·공개 임베드·작업 큐·감사 로그에는 암호문이나 원문을 복사하지 않습니다.

## 영속성과 운영 범위

안내 메시지는 추가 테이블 `panels`에 채널·메시지 ID를 저장합니다. 기존 이벤트·상품·당첨 스키마와 user_version 1을 유지하는 추가 테이블이므로 이전 코드의 이벤트 데이터와 호환됩니다. 슬래시 명령은 관리자용 init·setting 두 개입니다. setting은 READY 상태의 게시된 안내와 공개·검수 채널 설정이 있어야 열립니다. 기존 설치의 완료된 안내도 유지하며 공개 안내에는 일반 이용 버튼 네 개만 표시합니다. 상품·인증 첨부는 입력창의 File Upload로 수신하고 비공개 응답에만 표시합니다.

`draft_steps`에는 이어서 진행할 단계·자리와 선택 템플릿의 ID·revision을 저장합니다. `event_templates`는 공개 문구·허용/차단 역할·인증 설정만 저장하고 시간·인원·비공개 지급 내용을 포함하지 않습니다. 템플릿 적용 시 이벤트에 값을 복사하며 revision 변경은 재확인을 요구합니다. 기존 운영 테이블을 교체하지 않는 추가 테이블입니다.

`setup_sessions`에는 서버·관리자별 초기설정 초안과 무작위 토큰을 저장합니다. 채널/역할은 Label을 사용하는 실제 Modal에서 선택합니다. Modal 제출로 다른 Modal을 바로 열지 않고 비공개 다음 버튼으로 연결합니다. 최종 완료 전에는 운영 설정이나 공개 메시지를 변경하지 않습니다. 완료 시 설정을 저장하고 안내를 게시하며 전송 실패 시 초안을 유지해 같은 안내의 대조·재시도를 지원합니다. 완료 또는 취소하면 해당 초안을 삭제합니다.

`guilds.condition_roles`는 조건 선택 후보 목록입니다. 관리 권한 역할과 구분하며, 허용·차단 선택 메뉴는 String Select로 이 후보만 표시합니다. UI에서 반대쪽 선택을 제외하고 서버에서도 중복과 미등록 역할을 차단합니다. 공개 이벤트는 Components V2로 표시하며 기존 공개 이벤트도 동일 메시지 ID로 전환합니다. 주최자 중복 멘션과 내부 job 표시를 제거합니다.

당첨·마감 알림은 원본 이벤트의 start 작업에 기록된 채널을 사용하며 messageReference로 공개 메시지를 답장 대상으로 지정합니다. 원본 삭제 시 failIfNotExists=false로 일반 알림을 허용하고 repliedUser=false로 원본 작성자 추가 멘션을 막습니다. nonce/작업표식에 의한 결과 대조는 유지합니다.

## MySQL 저장소

DB_DRIVER로 저장소를 선택합니다. MySQL 연결은 전용 Worker에서 관리하고 기존 동기 저장소 계약으로 요청을 직렬화합니다. SQL 값은 준비된 문의 매개변수로 전달합니다. 호출자는 DB 응답을 기다리므로 봇과 가까운 네트워크의 DB를 사용하세요. 기본 제한시간은5초이며 연결·프로토콜·응답시간 오류가 나면 연결을 사용 불가 상태로 고정하고 자동 재연결/쿼리 재실행을 하지 않습니다. 실행 잠금 확인이 실패하면 봇이 종료되며, 기존 SENDING 복구 규칙이 중복 지급을 막습니다.

트랜잭션은 한 연결에서 BEGIN/COMMIT/ROLLBACK으로 처리합니다. DB 연결의 GET_LOCK과 기존 token/heartbeat를 함께 사용하며 BLOB은 AES-GCM 암호문 그대로 저장합니다. 지급 완료·인증 삭제는 SQLite와 같은 트랜잭션에서 해당 열을 NULL로 만듭니다. MySQL의 undo/binlog·복제·백업 보존은 DB 운영 설정 범위이며 SQLite secure_delete 설정과 동일한 물리 삭제를 뜻하지 않습니다.

단일 호스트의 단일 프로세스를 대상으로 합니다. DB 임대 잠금은 5초마다 갱신하고 60초 후 만료합니다. 잠금을 잃은 프로세스는 종료합니다. 작업 큐는 공개 알림과 상태 게시를 보존합니다. 검수 알림은 제출 버전에 묶어 오래된 요청으로 새 자료를 승인하지 못하게 합니다.

5초 스케줄러는 만료 시점 이후 최대 한 주기 안에 리롤을 처리합니다. 제출·수령 요청 자체는 현재 시각으로 판정하므로 스케줄러 지연을 이용해 기한 후 제출할 수 없습니다. 추첨 중 멤버 조회에 일시 오류가 있으면 해당자를 임의 탈락시키지 않고 추첨을 지연합니다.

기존 SQLite 백업에는 삭제 전 암호문이 남을 수 있습니다. 백업을 도입한다면 보관 기간·암호화 키 접근·삭제 정책을 함께 정해야 합니다. 현재 코드가 과거 백업이나 Discord 플랫폼 사본을 삭제하지는 않습니다.
